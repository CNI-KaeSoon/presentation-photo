# 07. 개발자 노트

코드를 수정할 때는 결과가 조용히 달라지는 계약부터 확인합니다.

## 핵심 불변식

1. `02_작업장/slide_tool/index.html`의 `COLOR_CORE`와 `05_스크립트/slide_color.py`는 같은 입력에 같은 픽셀 결과를 내야 합니다.
2. `--workers 1`은 기준 직렬 경로입니다. 병렬 경로의 출력 순서와 바이트 결과가 같아야 합니다.
3. 이미지 저장 키 `../<발표>/img/<파일>`과 `data.js`의 `file` 값은 그대로 유지합니다(발표 = `02_작업장` 안의 폴더 이름).
4. 원본 사진은 읽기 전용입니다.
5. 패키지 내부 경로는 현재 작업 디렉터리가 아니라 `Path(__file__)` 또는 계획 파일 위치를 기준으로 계산합니다.
6. `workflow.js`는 `heartbeat.js` 바로 다음에 둡니다. `index.html`의 발표 이름 변경 UI를 수정하더라도 COLOR_CORE 블록은 건드리지 않으며 sha256은 `d06f4a4ba88c58aa976983999f153f5ffd9986b78ff73787456d0005cbd50434`입니다.

## 브라우저 워크플로 API 계약

- 서버는 `Host`를 모든 요청에서, `Origin`을 모든 변경 요청에서, `X-Workflow-Token`을 `/api/token` 외 모든 API에서 검증합니다.
- 브라우저는 `GET /api/token` 뒤 아래 API를 씁니다. 파일 경로는 브라우저가 보내지 않고, 서버가 작업장·원본·결과 폴더 안에서만 해석합니다.
- 준비·PDF는 동시에 하나만 실행하는 잡입니다. `workflow.js`는 700ms 폴링으로 단계와 증분 로그를 읽고, 잡 실행 중에는 서버 워치독이 종료하지 않습니다.
- `regroup=true`(다시 나누기)는 발표 이름과 localStorage 키를 어긋나게 할 수 있으므로 자체 DOM 확인 모달을 반드시 거칩니다.
- 서버 응답의 파일명·상세 오류·로그는 `innerHTML`이 아니라 `textContent`로 표시합니다.

| 메서드·경로 | 용도 |
|---|---|
| `GET /api/status` · `GET /api/job` | 원본·발표·PDF 수, 환경, 원본 변경 여부 / 실행 중 잡의 단계·로그 |
| `POST /api/upload` · `/api/open-folder` | 사진 업로드(`lastModified` 보존) / 원본·결과 폴더 열기 |
| `POST /api/rename-group` | 발표 이름 변경(현재·새 basename만 전송) |
| `POST /api/prepare` · `/api/export-pdf` · `/api/job/cancel` | 사진 준비 · PDF 생성 · 잡 취소 |
| `POST /api/auto-detect` | 경계 자동 찾기. 요청 `{keys:[작업 이미지 키…], rotations?:{키:0~3}}`, 응답 `{results:{키:{corners|null, conf, review}}}`. 동기 응답이며 발표 전체는 클라이언트가 여러 번 나눠 부릅니다. 검출은 `auto_detect_api.py`를 venv 파이썬 하위 프로세스로 실행합니다 |
| `POST /api/new-event` | 새 행사 시작. 요청 `{backup?:{…}, moveOriginals:false}`. 발표 폴더·계획·목록을 작업장 안의 `_이전작업_YYMMDD_HHMM`으로 **이동**(삭제 없음), 선택 시 원본도 이동. `03_결과물`과 도구 파일은 건드리지 않음 |
| `GET /api/backups` | `03_결과물/백업/`의 백업 목록(최신 순, `slide_tool_backup_…json` 형식만) |
| `GET /api/backup?name=` | 백업 하나의 내용. 이름은 목록과 같은 정규식만 허용해 경로 탈출을 막음 |

`/api/status`의 원본 변경 감지는 준비 당시 계획과 현재 원본 폴더를 비교합니다. 화면의 "원본이 바뀌었습니다" 띠와 `그대로 준비` 차단이 이 값을 씁니다.

## 경계 자동 찾기

- `05_스크립트/auto_detect_screen.py`가 검출기 본체(OpenCV), `auto_detect_api.py`가 서버용 stdin/stdout 실행기입니다. 결과 경계는 원본 사진 정규좌표 `[TL, TR, BL, BR]`이라 그대로 `slideCorners_v1`에 넣습니다.
- 사용자가 사진을 90° 돌려 뒀다면(`rot`≠0) 그 방향으로 세워 검출한 뒤 파일 좌표로 되돌립니다. `toDisp/fromDisp`는 `index.html`의 같은 이름 함수와 같은 식이어야 합니다.
- 확신이 낮으면 `review: true`가 되어 화면에서 `확인 필요`가 됩니다.
- 정확도는 `05_스크립트/eval_auto_detect.py`로 잽니다. 사람이 손본 백업 JSON의 경계를 정답으로 삼아 모서리 오차(픽셀 거리/대각선)를 냅니다.

```bash
python3 05_스크립트/eval_auto_detect.py --backup <백업.json> --workspace 02_작업장 [--csv out.csv] [--jobs N]
```

### 자동 찾기 재학습

후보 사각형을 고르는 점수 모델(은닉 12 신경망)과 conf 환산값은 `auto_detect_screen.py`의 `# BEGIN AUTO-DETECT WEIGHTS` ~ `# END AUTO-DETECT WEIGHTS` 블록에 들어 있습니다. 행사 사진이 쌓이면 `05_스크립트/train_auto_detect.py`로 다시 학습합니다. 특징 추출은 `auto_detect_screen.py`의 함수를 그대로 불러 쓰므로 학습과 추론이 어긋나지 않고, 같은 입력이면(seed 고정, `--set` 순서 포함) 같은 가중치가 나옵니다.

1. 행사 후 브라우저 도구에서 손본 경계를 `백업 내보내기` 합니다(`03_결과물/백업/`).
2. 현재 가중치로 정확도를 먼저 재 둡니다(`eval_auto_detect.py`, 위 명령).
3. 학습합니다. 백업과 그 `02_작업장`을 `::`로 묶어 `--set`으로 주며, 행사가 여러 개면 반복합니다. `--cache <폴더>`는 특징 추출 결과를 남겨 다음 실행을 조금 줄입니다(선택).

   ```bash
   python3 05_스크립트/train_auto_detect.py \
       --set <백업1.json>::<작업장1> --set <백업2.json>::<작업장2> \
       --out weights.json [--cache 캐시폴더] [--jobs N] [--verbose]
   ```

   출력은 후보·특징 추출 → 폴더 단위 2분할 교차검증(hit@2%·hit@5%, 학습에 안 쓴 사진으로 잰 값) → 전체 학습 → conf 캘리브레이션 순서입니다. "전체 학습" 점수는 학습에 쓴 사진으로 잰 값이라 낙관적이므로, 새 사진에서의 기대치는 교차검증 값을 봅니다. 사진 380장·8코어급에서 약 1~2분 걸렸습니다.
4. 좋아 보이면 `--apply`를 더해 다시 돌리거나(`--from-weights weights.json --apply`는 학습 없이 저장된 결과만 적용) 가중치 블록만 교체하고, `eval_auto_detect.py`를 다시 돌려 전후를 비교합니다. 더 나쁘면 `git checkout 05_스크립트/auto_detect_screen.py`로 되돌립니다.

블록 밖의 코드는 건드리지 않으며, 블록을 손으로 고치지 않습니다(다음 `--apply`가 통째로 덮어씁니다). 사진·백업·`weights.json`은 작업 산출물이라 커밋하지 않습니다. 점수 열(특징)을 바꾸면 기존 가중치와 열 순서가 맞지 않으므로 반드시 재학습해야 합니다.

## 화면 구조 (index.html·workflow.js)

- **토큰**: `:root`에 색(`--primary` 등), 간격(`--s1`~`--s4`), 글자(`--f1`~`--f5`), 둥글기(`--r1`~`--r3`) 토큰을 둡니다. 새 스타일은 hex를 쓰지 않고 토큰을 씁니다.
- **컴포넌트**: 버튼 `.btn`(`primary`·`danger`·`ghost`·`sm`·`lg`·`icon`), 배지 `.badge`, 알림 띠 `.banner`(`info`·`error` 등), 토스트 `toast(msg, ms, {label,onClick})`, 메뉴 `openMenu({anchor|x,y, items})`, 대화 `openModal({title, html|node, ok, okKind, cancel, onOk, keepOpen, canClose, noCancel})`. `workflow.js`도 같은 `openModal`을 씁니다. 브라우저 기본 `alert`/`confirm`은 쓰지 않습니다.
- **헤더**: 단계 알약(`#hdrSteps`)과 "다음 할 일"(`#hdrNext`, 상태에서 계산한 메시지·버튼). 서랍(사진 넣기·준비·PDF)은 `workflow.js`가 그립니다.
- **사진 상태**: 미작업·자동·확인 필요·완료·제외·자료. 필터(`#navChips`)와 `jumpToState`(N 키)가 같은 상태 계산을 씁니다.
- **단축키 표**는 `index.html`의 `SHORTCUTS` 배열 하나이며, `?` 도움말이 이를 그대로 그립니다. 키를 추가하면 여기도 고칩니다.
- **용어**: 화면·문서는 발표(사진 묶음)·경계·모서리·손잡이·원래대로·되돌리기·PDF n개로 통일합니다.

## 백업과 경로 계약

백업 JSON의 localStorage 값은 문자열로 한 번 더 직렬화되어 있습니다. 경계(네 모서리) 순서는 `[TL, TR, BL, BR]`이고 좌표는 0~1로 정규화됩니다. 90° 회전은 이 배열 순서만 순환시켜 구현하므로(시계 `[BL, TL, BR, TR]`) 브라우저와 PDF가 함께 돌아가고, 백업 스키마는 그대로입니다.

`worktree.json` v2는 계획 파일 기준 POSIX 상대경로를 저장합니다. 읽을 때 현재 운영체제 경로로 해석하며, v1 절대경로 계획은 기존 경로 우선·이동 위치 폴백을 유지합니다.
